# ローカル収集キャッシュMCP構成を採用

- 状態：採用
- 日付：2026-08-10
- 対象シーズン：Season 0からSeason 1
- 決定者：リポジトリ所有者

## 背景

KUMA800は、山形県CSV、けものおと2の公開閲覧面、過年度KML等、確認段階と更新頻度が異なる複数情報源を扱う。

AIエージェントが問い合わせるたびに上流へアクセスすると、次の問題が起きる。

- AI側のタイムスケジュールが高頻度だと、同じ内容を何度も取得する。
- 複数AIまたは同時tool callが、上流へ重複リクエストを送る。
- ベンダーと行政のインフラ費を無駄に増やす。
- 上流障害時に検索機能まで同時に失う。
- 取得、正規化、近傍検索、ユーザー位置管理の責任がAI promptへ漏れる。

## 判断

KUMA800は、利用者端末上で常駐するMCPサーバーを、**収集scheduler、scraper wrapper、正規化schema、SQLite cache、ユーザー位置YAML、AI向けinterface**の統合境界として採用する。

```text
山形県CSV ───────────────┐
けものおと2公開閲覧面 ──┼→ scraper wrapper → 正規化 → SQLite
過年度KML ───────────────┘                        │
                                                   │
users.yaml ───────────────→ 問い合わせ時だけ近傍計算
                                                   │
AIのタイムスケジュール → MCP interface → cache応答┘
                               │
                               └→ TTL超過時だけ収集予約
```

AIは上流URL、HTML、CSV、公開共通ID、取得間隔を管理しない。ユーザー位置をMCPへ登録・参照し、近傍signal、鮮度、情報源状態を取得する。利用者が接続したAIへの位置情報の返却は、意図したinterfaceであり漏えいとは扱わない。

## コンポーネント

### 1. SQLite：クマ観測と収集状態

SQLiteには公開情報源から得たクマ観測、出典、収集実行、cache状態を保存する。ユーザー位置は保存しない。

最低限のtable候補：

- `sources`：情報源ID、種類、URL、最小取得間隔、TTL、有効状態
- `fetch_runs`：開始・終了時刻、HTTP状態、最終URL、ETag、Last-Modified、hash、成否、失敗理由
- `sightings`：正規化した観測、位置、時刻、確認段階、入力種別、出典
- `sighting_links`：異なる情報源にある同一候補・訂正・置換関係
- `source_state`：最終成功、次回取得可能時刻、連続失敗数、backoff、直前正常snapshot

SQLiteはWAL modeを使用し、MCP問い合わせと収集処理の同時実行を許容する。初期規模では空間拡張を必須にせず、緯度・経度のbounding boxで候補を絞り、Python側のHaversine計算で距離を確定する。

### 2. YAML：利用者位置と検索条件

ユーザー位置はSQLiteへ混ぜず、ローカルYAMLへ保存する。

候補項目：

```yaml
version: 1
users:
  local-user:
    latitude: 38.0
    longitude: 140.0
    radius_km: 10
    timezone: Asia/Tokyo
    enabled: true
```

- YAMLはGit管理しない。
- 既定pathはOSのuser data directory配下とし、repository内へ置かない。
- ファイルpermissionは可能な環境で所有者のみ読み書き可能にする。
- 原子置換で更新し、壊れたYAMLで直前正常値を消さない。
- クマ観測とユーザー位置は保存時に結合しない。近傍検索時だけmemory上で突合する。
- MCP toolは、利用者が認可したAIへ保存位置または近傍計算に必要な位置を返してよい。

### 利用者位置の責任境界

KUMA800が防ぐのは、利用者位置がGit、P2P、fixture、公開ログ、上流scrape先、公開観測DBへ意図せず流れることまでとする。

KUMA800へ接続するAI、MCP client、ローカルhost、OSは利用者が選択・管理する信頼領域である。これらが敵対的で、正規のMCP応答から位置情報を取得して外部へ持ち出す場合は、KUMA800の脅威モデル外とする。KUMA800は、悪意ある接続先AIに対するDRM、難読化、位置秘匿、安全保証を提供しない。

この境界はリスクの不存在を意味しない。接続先AIが位置を外部送信する可能性は、利用者がAIと端末を選ぶ際のリスクである。ただし、その投機的リスクを減らすために、クマ近傍判定へ必要な位置精度やMCP応答を自動的に欠落させない。現実のクマ危険を優先する。

### 3. scraper wrapper

各情報源は共通protocolへ合わせる。

```text
inspect()       情報源の能力と現在状態
fetch()         制限付き取得
parse()         上流固有形式の解析
normalize()     共通観測schemaへの写像
```

最初のadapter候補：

- `yamagata_csv`：行政整理済みsnapshot候補
- `kemonote2_web`：公開共通IDを使う非公式スクレイピング観測源
- `yamagata_r7_kml`：過年度比較用

adapterは、取得可能性を公式提携・公式API保証へ変換しない。各観測へ取得方法と情報源分類を残す。

### 4. 正規化schema

最低限、次を保持する。

```text
source_id
source_kind
source_event_id
source_url
fetched_at
observed_at
event_time
latitude
longitude
location_precision
input_kind
review_state
animal_kind
count
original_text
content_hash
supersedes
```

`review_state`候補：

- `provisional`：一次通報、IoT、未確認signal
- `reviewed_candidate`：行政整理済みと推測されるが確認工程は未確認
- `confirmed`：確認主体と工程を追跡できる
- `unknown`：確認段階不明

異なるsourceの近接レコードを自動的に同一事象へ潰さず、`sighting_links`へ関連候補として保存する。

### 5. 収集schedulerとcache

上流取得頻度はAIの問い合わせ頻度から切り離す。

- sourceごとに`min_fetch_interval`とTTLを持つ。
- AIが短時間に何度問い合わせても、SQLite cacheから返す。
- TTL超過時は収集を予約するが、同じsourceの同時fetchはsingle-flightにする。
- `ETag`と`Last-Modified`が使える場合は条件付きGETを優先する。
- 失敗時は指数backoffし、直前正常cacheを削除しない。
- stale cacheを返す場合は、古さと失敗理由を必ず返す。
- `SOURCE_CHANGED`、`SOURCE_UNAVAILABLE`、`STALE`をクマ不在へ変換しない。
- background schedulerの周期とAI側の問い合わせ周期を独立設定できるようにする。

### 6. MCP interface

AI向けの最小interface候補：

- `kuma.user.upsert`：利用者位置と検索半径をローカルYAMLへ保存
- `kuma.user.get`：保存済み条件を確認
- `kuma.sightings.nearby`：cacheから近傍signalを取得
- `kuma.data.freshness`：source別の最終成功時刻と古さを取得
- `kuma.sources.list`：source分類、公式性、取得方式、状態を取得
- `kuma.sync.status`：scheduler、backoff、次回取得予定を取得
- `kuma.sync.request`：強制fetchではなく、TTLと最小間隔を守る更新要求

`kuma.sightings.nearby`は、最低でも次を返す。

- 観測一覧と距離
- provisional／reviewed等の確認段階
- 取得時刻と事象時刻
- sourceと原典参照
- cacheの鮮度
- 0件でもクマ不在を保証しない警告

## cacheの責任境界

MCP cacheは上流への無駄打ちを止めるが、次を保証しない。

- 上流に存在する全情報の取得
- リアルタイム性
- クマの不在
- 速報signalの正しさ
- 行政確認工程の代替

cache hitは「前回取得物を返した」であり、「現在も安全」を意味しない。

## 根拠

- 利用者位置をGit、P2P、公開DB、上流scrape先へ混ぜず、利用者が認可したAIへはMCP機能として必要な範囲を返せる。
- AIの高頻度scheduleが上流負荷へ直結しない。
- 上流停止中も、鮮度表示付きで直前観測を参照できる。
- CSV、画面、KMLの異なる意味を焼却せず統合できる。
- scraper変更とMCP interfaceを分離できる。
- SQLiteとYAMLは導入・バックアップ・検査が容易で、Season 1の規模に適する。

## 代替案

### AIが必要時に直接scrapeする

棄却。取得頻度、cache、認証、parser、障害処理が各AIへ分散し、上流への無駄打ちを制御できない。

### ユーザー位置もSQLiteへ保存する

初期設計では棄却。公開観測DBと個人位置のbackup・共有境界が結合する。将来、複数ユーザー、位置履歴、transactionが必要になれば再検討する。

### 全観測をYAML／JSONへ保存する

棄却。差分更新、期間検索、近傍候補抽出、重複関係、同時読み書きが複雑になる。

### 外部PostgreSQL／クラウドDBを使う

Season 1では棄却。ローカルファースト要件に対して運用費と依存が大きい。

## 影響

- SQLite migrationとYAML schema versionが必要になる。
- scraperはMCP toolから直接呼ばず、service層を経由する。
- scheduler停止中でもqueryはcacheを読める。
- 個人位置を含むYAMLのbackup、permission、削除機能が必要になる。接続先AIによる二次利用はKUMA800の管理外であることをinterface文書へ明示する。
- MCP serverが常駐しない環境では、query時の期限付き更新requestをfallbackとして用意する。

## 不明点

- PythonとMCP libraryの最終選定。
- background schedulerをprocess内taskとするか、OS schedulerへ委譲するか。
- YAML serializerとschema validator。
- SQLite migration toolを使うか、標準libraryで小さく管理するか。
- けものおと2画面で取得可能な項目、ID、更新時刻、訂正表現。
- sourceごとのTTL、最小取得間隔、最大backoff。
- raw responseを保存する範囲と、個人名・精密位置を除去する段階。

## 見直し条件

- 観測件数または同時利用者数がSQLiteの運用範囲を超えたとき。
- ユーザー位置履歴や複数端末同期が必要になったとき。
- 行政またはベンダーから公式API、push通知、差分feedが提供されたとき。
- sourceの利用条件または公開境界が変わったとき。
- 常駐schedulerを維持できない実行環境を主要対象にするとき。

## 次の実装単位

1. Python package skeletonと設定pathだけを作る。
2. SQLite migration、repository、正規化schemaを実装する。
3. YAML user storeをpermission・原子更新込みで実装する。
4. fake scraperでTTL、single-flight、stale cache、backoffを試験する。
5. MCP interfaceをcacheだけに接続する。
6. 山形県CSV adapterを追加する。
7. けものおと2は低頻度の観測probeから始め、schemaを確定する。
