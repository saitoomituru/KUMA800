# 0006 KUMA800の独立開発を終了し成果を保存する

状態: 採用

制定authority: repository所有者 saitoomituru（会話で終了計画の実行を指示）
対象: KUMA800独立開発、今季運用計画、Season 1〜3の残作業
保存実装revision: `edf56b3fef1a81ecbd06673f2dc50ed9f112faf0`

## 背景

所有者の報告では、今季は電力問題によって先に頓挫した。FQuery／Sphereが並行して進展し、独立したKUMA800の開発・常駐運用計画を維持する選択から、成果保存と必要時の部品再利用へ切り替える。

元の目的は、地域の物理危険情報を出典・鮮度付きでAIへ届け、AIの都合による観測の改変・削除を機械的に防ぐことだった。この目的、コード、設計判断、試験、既知課題は保持する。

## 判断

- 独立開発と今季運用計画を終了し、お蔵入りにする。通常の機能追加、実機調達、live probe、継続取得の新規実施を予定しない。
- ソース、fixture、lock、過去ADR、receipt、Issueを保存する。DBや履歴の削除は終了処理に含めない。
- FQuery／Sphereへ移植完了とは表示しない。必要な個別MCP plugin、fact adapter、実行境界として再利用できる候補に留める。
- 電力回復だけで自動再開しない。再開には用途、電力、運営主体、検証資源を確認した新判断を残す。
- #1／#4等の旧「物理収集継続」「定期確認」「条件成立で解凍」は歴史記録として保持し、今後のKUMA800運用判断は本ADRが置き換える。

## 今回のプロジェクト管理上の検証

失敗点の一つは、非線形な依存を持つマイクロモジュール群に固定の優先順位・線形進行計画を被せたことだった。#2のPhase A〜Fは、技術上の前提条件と作業優先順位を同じ一本道へ近づけた。

電力停止が直接の資源event。線形計画は、電力・実機・人間受入・別component進展が変わったときに、実行可能なbranchの再選択を難しくした管理上の問題として記録する。電力不足そのものが線形計画で発生したとは主張しない。

回収する運用原則:
- 全体の固定優先queue・一本道roadmapを極力避ける。
- モジュールごとの入出力、責務、接続契約、真の依存、fixture代替可能性、起動条件、資源、停止条件、保存成果を管理する。
- 局所の不可欠な実行順序と全体の作業優先順位を分ける。
- 資源・接続先・需要のeventに応じて実行可能なbranchを選ぶ。
- 非linear管理が常に成功するという母集団一般化ではなく、今回の事例で確認した教訓として残す。

詳細: [Manifest検証Note](https://github.com/saitoomituru/ZeroRoomLab-manifest/blob/main/note/20261004-1828__KUMA800終了と非線形依存の計画検証.ja.md)

#6にはSTALE保存後のenqueue失敗で再実行intentが失われる既知課題がある。通常経路PASSを耐故障境界全体PASSへ昇格しない。
#7のbackoff解除管理tool・live backoff受入、長時間運用も未確認のまま保持する。

保存実装の[Linux CI](https://github.com/saitoomituru/KUMA800/actions/runs/33293804937)はsuccess。今回、実機試験やlive取得を再実行した結果ではない。

## 代替案と影響

独立アプリの継続、電力回復待ち、全量移植は今回採用しない。移植を終了条件にすると終了のための新規実装が増えるため、保存と再利用を分ける。
forkと研究目的の再利用は既存licenseの範囲で可能。第三者データ、利用者位置、secretをコードと一緒に移さない。

## 停止・確認境界

今回の実行環境から所有者実hostのMCP／worker／LaunchAgent／Task SchedulerやDBを確認・停止できていない。実hostの停止済みとは表示しない。
GitHubのrepository archive設定は文書・Issue整理の後に行う管理操作。利用可能なAPIにその操作がない場合は未実施として報告する。公開文書の「独立開発終了」とGitHubのarchived flagを混同しない。
