## 観測事実

### [FACT] Wave 2 保存境界

- `kuma.sqlite3`にmigration、source、fetch run、観測、主張、source stateを実装した。
- 観測と主張はSQLite triggerでもUPDATE／DELETEを拒否する。
- application writeは`ObservationIngestStore`へ限定し、read-only接続はSQLiteの`mode=ro`と`query_only`を使う。
- 同じsource event IDと内容hashの再ingestは同じ観測へ収束する。上流内容hashが変われば別観測として残す。
- `users.yaml`は観測DBと分離し、OS標準user data directoryを既定とする。`KUMA800_DATA_DIR`を指定したservice群とは同じdata directory契約を使う。
- YAMLはschema version 1、原子置換、可能な環境で所有者read/writeのみ、破損した既存fileを自動上書きしない条件を試験した。

### [FACT] Wave 3 DUMMY-KUMA

- Hueyの永続queueを`queue.sqlite3`、観測正本を`kuma.sqlite3`へ分離した。
- FastMCPとは独立するforeground consumer entrypointとして`kuma800-worker`を追加した。
- macOS／Windows共通baselineはHueyの`thread` worker 2本である。worker processとFastMCP processを分離する設計であり、各taskを個別processへ隔離したという意味ではない。
- testは別Python processでtaskをenqueueし、別consumer processがDUMMY-KUMAを観測DBへappendするところまで通した。
- DUMMY-KUMAは外部networkへ接続しない。同じevent ID／内容hashを返し、二回のfetch runから観測一件へ冪等収束した。
- sourceごとに`STARTED`を一件だけ許すpartial unique indexを追加した。
- consumer起動時、15分より古い`STARTED`を`STALE`へ遷移させる回収処理を追加した。

### [FACT] Wave 4 FastMCP

- FastMCP 3.4.7をexact pinした。公式versioning方針がminor releaseでも破壊変更の可能性を明記しているため、更新はlock更新と回帰試験を伴う明示作業にする。
- MCP serverは`127.0.0.1`固定のStreamable HTTPとして別process起動する。portだけ`KUMA800_MCP_PORT`で変更できる。
- in-memory MCP transportでtool schemaとstructured resultを検証し、別processのloopback HTTP endpointからtool一覧を取得した。
- 観測面は固定SELECTだけを公開する。任意SQL、観測INSERT／UPDATE／DELETEはtoolにしない。
- scrape requestはHueyへenqueueしてtask IDを返し、同じMCP request内で完了を待たない。
- 利用者YAMLのlist、get、upsert、deleteをMCP protocol越しに往復した。

### [FACT] Wave 5 部分復旧

- 未知source IDはqueueへ入れる前にMCP requestを拒否し、見かけ上の`QUEUED`を返さない。
- 古い`STARTED`を残した状態から別consumer processを起動し、起動時に`STALE`へ回収するprocess smokeを通した。
- test用`queue.sqlite3`を削除・再作成しても、別fileの`kuma.sqlite3`にある観測一件が残ることを確認した。
- retry、backoff、thread hang、Huey result retentionは未実装のため、Wave 5全体はgreenではない。

## 自動補完した仕様穴

### [INTERPRETATION] runtime path

`KUMA800_DATA_DIR`があればそれを使用し、なければ`platformdirs`のOS標準user data directoryを使う。queue、観測正本、利用者YAMLを同じdirectory内の別fileとして扱うため、service managerは一つの環境変数だけを固定すればよい。repository内は既定保存先にしない。

### [INTERPRETATION] DUMMY pollとstale閾値

- DUMMY scheduler：5分間隔
- stale回収：起動時に15分超の`STARTED`

これはSeason 1のprocess pathを検証する暫定値であり、実データ源の取得間隔、安全上の鮮度保証、障害復旧SLOではない。山形県CSV adapter導入時は、公開頻度、取得時間、timeout、backoffの実測に合わせてsource別設定へ移す。

### [INTERPRETATION] YAML同時writer

Season 1は単一FastMCP control-plane processだけが`users.yaml`を書く前提なので、同一directory内の原子置換までを実装した。複数MCP processや外部editorとの同時更新を許す段階では、世代番号またはfile lockを追加する。現段階で不要なlock daemonを増やさない。
