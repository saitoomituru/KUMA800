## 1. 目的

今回のブレストで得た「FastMCPは常駐serverにできるが、定期収集workerと同一processへ詰める必要はない」という理解を、KUMA800の実装可能なarchitectureへ写像する。

完璧な最終形を先に作るのではなく、次の三点をSeason 1の判定軸にする。

1. AIからfake収集を依頼し、別processのworkerが処理し、SQLiteへ保存し、AIが読み返せるまで一本のpathが通るか。
2. server、worker、queueのどれかが停止しても、直前正常観測を焼却せず復旧できるか。
3. scraper meta記述、動的ON/OFF、Cockpitを後から接続するseamを塞いでいないか。

## 5. 観測

### [FACT] repositoryの現在地

- 実装code、package skeleton、lockfile、test pipelineはまだない。
- SQLite、YAML、MCP、scraper protocolは設計判断として存在するが、runtimeは未実装である。
- 所有者が手動で追加した直近commitは、KUMA800を「索敵・提示」へ限定し、判断権限と物理作用を外部へ送るものだった。
- ADR 0001はMCP server内へschedulerを配置していた。
- ADR 0002はscraper install、動的ON/OFF、registryをSeason 1に近い実装単位としていた。

### [FACT] FastMCP

- HTTP transportで起動したFastMCP serverはrequestごとに終了するCLIではなく、停止されるまでrequestを受けるserver processである。
- lifespanはserver起動時と終了時のresource管理を提供する。
- serverが常駐できることは、長時間task、定期polling、taskのdurable再試行まで自動的に解くことを意味しない。

### [FACT] Huey

- Hueyはqueue、consumer、scheduler、periodic task、retry、複数workerを提供する。
- SQLite backendを選択でき、Season 1でRedis等の別serverを必須にせず始められる。
- process workerはscraper同士を隔離しやすいが、強制終了中のtaskはapplication側の冪等性とstale回収を必要とする。

### [FACT] OS常駐

- FastMCPとHueyのどちらも、macOSとWindowsへの製品共通service登録そのものをKUMA800向けに完成させるものではない。
- `py-simple-service-manager`は複数OSのservice登録を包む候補だが、調査時点でalpha表記であり、WindowsではService Control ManagerではなくTask Schedulerを使う設計である。
- したがって候補発見と製品採用は分け、実機でboot/login起動、再起動、停止、logを比較する必要がある。

## 6. 考察

### [INTERPRETATION] FastMCPとHueyは兄弟serviceがよい

FastMCPをcontrol plane、Hueyをdata planeとすれば、AIとのtransactionが終了してもworker scheduleは残る。逆にworkerが落ちても、FastMCPは直前正常cacheと鮮度・停止状態を返せる。

この構成にKUMA800専用のmeta-daemonは不要である。二つのserviceをOS service managerへ登録すれば、親processを自作するより責任が小さい。

### [INTERPRETATION] durable queueは観測の正本ではない

`queue.sqlite3`は「これから何をするか」の可変状態であり、`kuma.sqlite3`は「何を観測したか」の追記型記録である。両者を分けると、queueの再構築やworker変更がクマ観測の焼却へ伝播しない。

### [INTERPRETATION] 最初の縦切り

```text
FastMCP sync request
  → Huey queue
  → fake scraper process
  → RawArtifact
  → SourceRecord
  → CandidateObservation
  → core ingest transaction
  → kuma.sqlite3
  → FastMCP read-only query
```

このpathが通れば、実データadapter、service登録、Cockpitを独立に差し替えられる。最初からCSV、けものおと2、KMLを全部完成させる必要はない。

### [INTERPRETATION] 所有者が責務限定を手動commitした理由

直近の`8427b99 [責務] KUMA800をクマ索敵と提示に限定`と`d4c3c67 [台帳] KUMA800索敵責務の判断を登録`は、code生成の不足を補うcommitではなく、KUMA800が持つ権限の上限を所有者自身が固定したものと推察する。

MCP、worker、IoTの接続を検討すると、技術的には「観測できるなら通報・罠・電気柵まで動かす」方向へ責務が膨らみやすい。しかし、索敵から物理作用への権限昇格はarchitecture上の便利さでは決められず、事故時の責任主体とプロダクトの存在目的を変える。このため所有者が手動でcommitし、人間のdesignation authorityとして境界を置いた可能性が高い。

この推察はcommit messageとdiffからの解釈であり、所有者本人の理由を証明する事実ではない。今回の設計では、その手動境界を上書きせず、FastMCPとHueyのどちらにも物理作用・自動通報を入れない。

### [HYPOTHESIS] 専用writer processはまだ不要

Season 1の件数なら、複数workerが同じcore ingest APIを呼び、SQLite transactionとunique constraintで直列化する構成で足りる可能性が高い。lock競合を計測する前に単一writer serviceを追加すると、queueが二重になり復旧状態が増える。

これは未検証の仮説であり、負荷試験で覆りうる。

## 9. 開発・test pipeline案

### pull requestごとのoffline gate

1. formatとlint
2. type check
3. unit test
4. migrationを空DBと一世代前DBへ適用
5. fake scraperの成功、timeout、壊れたpayload、重複再実行
6. read-only SQLのwrite拒否
7. `git diff --check`と文書link検査

実上流への接続成功は通常PRの必須gateにしない。上流停止や変更をcode品質失敗へ混ぜないため、live probeはschedule実行または明示的手動jobへ分離する。

### process smoke

- FastMCPとHueyを別processで起動する。
- 同一sourceの同時要求が一回のfetchへ束ねられることを確認する。
- workerをtask途中でkillし、stale回収と冪等再実行を確認する。
- MCPだけを再起動し、periodic taskが二重化しないことを確認する。
- `queue.sqlite3`再作成後も`kuma.sqlite3`が残ることを確認する。

### OS matrix

- macOS：launch/login、異常終了後restart、正常shutdown、log
- Windows：spawn process、login/boot、restart、shutdown、pathとpermission
- Linux：主要対象になった時点でsystemd adapterを追加
